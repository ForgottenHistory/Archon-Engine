# Scripting

**Status:** Implemented (`Scripting` assembly; its tests pass in the editor; not yet used by a game in play mode)
**Layer:** ENGINE mechanism; the GAME decides what scripts are for and what they can touch

## Purpose

Content that is logic (what an event does, when a decision is available, how much an AI wants something) is
better written as script than as C#: it can be changed without a recompile, written by people who don't touch the
engine, generated by tools, and shipped by mods. The engine runs Lua 5.2 for this, through the
[Lua-CSharp](https://github.com/nuskey8/Lua-CSharp) interpreter (pure C#, MIT; see `Scripts/Scripting/Plugins/README.md`).

Lua was chosen because it is common: there is documentation, tooling and editor support for it, and AI assistants
read and write it well. A format of our own would have none of that.

The engine provides the machinery only: a sandboxed Lua world, a way to give it C# functions and objects, and a
way to call into it. It defines no script functions about provinces, countries or anything else. Those are the
GAME's.

## The shape of a scripted system

1. The GAME makes a `ScriptEngine` and gives it its vocabulary: global functions (`SetFunction`) and object types
   with methods (`DefineType`, `ScriptType.SetMethod`).
2. The GAME runs its script files (`RunFile`). A script file registers content by calling the GAME's functions
   with tables:

   ```lua
   decision {
     id = "raise_taxes",
     cost = 50,
     available = function(c) return c:stability(">", 0.5) and not c:at_war() end,
     effect = function(c)
       c:add_gold(200)
       c:add_stability(-0.05)
     end,
   }
   ```

3. The GAME's `decision` function reads the table (`ScriptTable`): the values now, the functions as
   `ScriptFunctionRef` to keep.
4. Later, the GAME calls a kept function with the object it is about (`engine.CallBool(available, country)`,
   `engine.Call(effect, country, out _)`).

## API

| Type | What it is |
|---|---|
| `ScriptEngine` | One Lua world. `SetFunction`, `SetGlobal`, `GetGlobal`, `DefineType`, `Run`, `RunFile`, `Call`, `CallBool`, `CallNumber`, `LastError`, `Error`, `MissingMember`, `Missing`, `MissingCalls`, `LogMissing`, `InstructionLimit` |
| `ScriptFunction` | Delegate of a C# function scripts call: `(ref ScriptCall call)` |
| `ScriptCall` | One call: arguments (`Count`, `[i]`, `Number`, `String`, `Bool`, `Object<T>`, `Self<T>`, `Table`, `Function`), result (`Return`, `ReturnList`), `Fail`, `Engine` |
| `ScriptType` | A kind of object: `SetMethod`, `HasMethod`, `MethodNames` |
| `ScriptObject` | Base class of the GAME's objects scripts hold (a country, a province) |
| `ScriptValue` | nil, boolean, number, string, function, table or object; C# values convert to it |
| `ScriptTable` | A Lua table read from C#: fields by name, a list by position (from 1), `FieldNames` in a fixed order |
| `ScriptFunctionRef` | A Lua function kept to call later |

No type of the Lua library is in the public API, so game code never references `Lua.dll`, and the interpreter
can be replaced inside the `Scripting` assembly alone.

### Objects and methods

```csharp
sealed class CountryScope : ScriptObject
{
    public readonly ushort Id;
    public CountryScope(ScriptType type, ushort id) : base(type) { Id = id; }
}

var country = engine.DefineType("country");
country.SetMethod("add_gold", (ref ScriptCall call) =>
{
    var c = call.Self<CountryScope>();      // argument 0 of a method is the object
    economy.AddGold(c.Id, call.Number(1));  // c:add_gold(200) -> 200 is argument 1
});
```

- Keep **one object per thing** (one `CountryScope` per country, made once). Lua compares objects by identity,
  so `a:owner() == b` is true only when both are the same C# object. It also means no allocation per call.
- An argument that is missing or of another kind reads as the fallback, so each function decides what it
  requires. `call.Fail("message")` stops the script with an error.
- A method can call back into the script: `call.Engine.CallBool(call.Function(1), other)` runs a function the
  script passed (`c:any_neighbor(function(n) return n:at_war() end)`).

## Rules scripts run under

- **Synchronous.** `Run` and `Call` return when the script has finished. A script cannot wait, so scripts are
  safe to call inside a command or a tick.
- **Sandboxed.** The `base`, `string`, `table`, `math` and `bit32` libraries only. There is no `io`, `os`,
  `debug`, `package`, `require`, `load`, `loadstring`, `dofile`, `loadfile` or `collectgarbage`. `print` writes
  to the log. An object's metatable is out of reach.
- **Bounded.** A top-level call that runs more than `InstructionLimit` instructions (default 50 million, checked
  every 100 000) is stopped with an error, so an endless loop cannot freeze the game.
- **No failure escapes.** A syntax error, a runtime error or a C# function throwing makes `Run`/`Call` return
  false. `LastError` has the message with the script's file and line, `Error` fires, and it is logged as a
  warning. The engine is usable afterwards.

## Determinism

Lua numbers are doubles, and Lua state is not saved. For a deterministic, saveable simulation:

- **Do the arithmetic in C#.** Scripts pass numbers (mostly literals) to C# functions, which convert them to
  fixed point and do the maths there. The same literal is the same double on every machine. Do not compute
  simulation values in Lua and feed them back.
- **Keep state in C#.** Flags, variables and counters that a script sets go through GAME functions into game
  state, where they are saved and synchronised. A Lua global or upvalue is lost on load and never synced.
- **No `math.random`.** It is removed. The GAME provides its own random functions on a deterministic generator.
- **Ordered iteration only.** `pairs` over a table has no guaranteed order. Give scripts lists (`ReturnList`)
  to loop with `ipairs`, and read table fields from C# by name or through `FieldNames` (ordinal order).
- **Change state through the same path as everything else.** A script's effect should run where a command
  would (inside the command that triggered it), not from UI code.

## Things that are missing

A script written before the GAME implements everything it calls should still load and mostly work:

- A **method a type lacks** does not fail the script. It is reported once (`MissingMember`, `Missing`, a logged
  warning) and returns false. `ScriptType.HasMethod` tells real methods from these.
- A **missing global** is a normal Lua error ("attempt to call a nil value"), unless the engine is made with
  `stubMissingGlobals: true`, which treats globals the same way as methods. Use that for scripts converted from
  another format; leave it off for hand-written scripts, where it would hide typos.

`Missing` is the to-do list: every name content uses that the game does not provide yet. With a large converted
set that list runs to hundreds of names: set `LogMissing = false` to keep them out of the log and collect them
from `MissingMember` instead.

A missing trigger answers false, so a negation of it answers true. `MissingCalls` counts every call of something
missing: read it before and after a call, and when it grew, treat the answer as "can't tell" where a wrong yes
would do something.

A missing method returns false, so a script that calls a method on its result (`c:missing():other()`) or loops
over it (`ipairs(c:missing_list())`) still fails there. A GAME with such content can soften that in Lua it runs
first (an `ipairs` that accepts a non-table as an empty list) and by returning a stand-in object, about which
everything is false, where a lookup finds nothing.

## Cost

Measured on .NET 8 with the same interpreter (Unity's Mono will be slower): a Lua function with two C# calls
about 1 microsecond with no allocation; a method that calls a Lua function back for each of 50 objects about
2.5 microseconds; loading 12 MB of Lua source (11 000 registered tables with functions) about 0.7 seconds.

Calls are cheap enough for decision points (an AI choosing, a tooltip opening, an effect firing). They are not
meant for per-province work every tick: keep that in C#.
